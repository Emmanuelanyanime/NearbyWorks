# NearbyWorks frontend

Public, authentication, and account views share the design system in `css/app.css`, Alpine interactions in `js/app.js`, and the components in `views/components/`.

From the repository root, rebuild the frontend with:

```sh
node resources/build-frontend.mjs
```

This uses the existing Vite configuration and dependencies, writes its manifest and versioned bundles to `public/asset/nearbyworks/`, and preserves the downloaded images and logos there. The shared head reads that manifest. The root `npm run build` command still uses its original output directory; use the command above for these views.

## Jobs, categories and the hero map

- Job data is prepared in one place, `app/Support/JobCatalog.php`. Until a live feed exists it reads the placeholder listings in `resources/data/sample-jobs.php`; pass real jobs to the `Home`, `Jobs` and `JobDetail` views as `$jobs` (same keys) and the samples are ignored. Only `id` and `title` are required.
- Categories are built from the jobs' `field` values (icons come from `resources/data/job-categories.php`), so an empty category never shows.
- The hero map (`resources/js/hero-map.js`) puts one flag marker on each country that has jobs. Cities and countries are matched against `resources/data/places.php`; add rows there when a place does not appear. Remote-only locations get no marker. Flags are `public/asset/nearbyworks/flags/{code}.svg`; add a file there for any new country.
- The dotted land comes from `resources/js/world-land.js`, generated by `node resources/build-world-dots.mjs` (downloads Natural Earth outlines). You only need to re-run it to change the dot grid.
- The map animates only on screen and stays still for people who prefer reduced motion. Colours come from the `--map-*` variables on `.nw-hero__map` in `css/app.css`, so dark mode follows automatically.

Photography and third-party resource-logo provenance is documented in `public/asset/nearbyworks/SOURCES.md`. Those logos identify independent outbound links. NearbyWorks uses its own text wordmark.

Routes, controllers, models, database configuration, and dependencies are outside this frontend change. Account forms retain existing endpoints and validation fields; registration sends the first and last name fields required by its current controller. The existing backend mixes these fields with a `name` database/profile contract, which needs a separate backend correction.
